# تحویل کد فاز ۲

## وضعیت تحویل
این نسخه اصلاح کد روی ZIP ارسالی است، نه تأیید اجرای سایت در محیط واقعی. ساختار `api/` و `web/` حفظ شده؛ فایل‌های جدید و ویرایش‌شده در `PHASE_2_FILES.md` و فایل JSON کنار آن مشخص‌اند. هیچ تغییری روی مخزن GitHub، هاست یا دیتابیس زنده انجام نشده است.

**پیش از انتشار، اجرای migration، تست‌های Laravel، ساخت کامل Next.js و آزمون مرورگر با مسئولیت مجری است.** PHP، Composer، Docker و وابستگی‌های نصب‌شده پروژه در محیط تهیه این خروجی موجود نبودند؛ دسترسی اینترنت برای نصب وابستگی‌ها نیز در این محیط وجود ندارد.

## قابلیت‌های پیاده‌سازی‌شده
- پنل مالک در `/dashboard`: ثبت و ویرایش نام، دسته‌بندی، خدمات، توضیحات، تلفن، ایمیل، آدرس، شهر و محله.
- موقعیت کسب‌وکار مستقل از موقعیت جستجوی کاربر است؛ انتخاب روی نقشه یا ورود مختصات، با امکان پاک‌کردن هر دو مختصات.
- شبکه‌های اجتماعی قابل افزودن/حذف؛ واتساپ شماره ایران/بین‌المللی را به `wa.me` تبدیل می‌کند. فیلد خالی در ذخیره، داده قبلی را واقعاً پاک می‌کند.
- لوگو و کاور با محدودیت نوع/حجم/ابعاد و گالری مستقل پنج‌تصویری، بدون نیاز به اشتراک.
- مدیریت کسب‌وکارها در `/admin/businesses`: همه وضعیت‌ها، جستجو و صفحه‌بندی، بررسی داده و تصاویر، تأیید/رد/تعلیق، دلیل تصمیم، نشان‌های `verified`، `featured` و `trusted`، تاریخچه رخدادها.
- لینک ثابت `/b/{slug}` و QR واقعی SVG با مقصد از `FRONTEND_URL`، نه دامنه API یا Host درخواست.
- صفحه عمومی فقط برای `approved`؛ تماس، نشانی، خدمات، شبکه‌ها، نشان‌ها و گالری از داده ذخیره‌شده خوانده می‌شوند. ویترین اشتراکی قبلی نیز جداگانه نمایش داده می‌شود.
- بخش‌های کارت‌ساز، طراحان، اشتراک، CMS و مسیرهای قبلی حذف نشده‌اند. فرم و صفحه عمومی برای پوشش کامل قرارداد بازآرایی شده‌اند؛ بازسازی پیکسلی ظاهر قدیمی هدف این نسخه نیست.

## قواعد انتشار
- ساخت پروفایل: `pending`.
- ذخیره بدون تغییر واقعی: وضعیت فعلی حفظ می‌شود.
- تغییر واقعی پروفایل، لوگو، کاور یا گالری: بررسی مجدد؛ نشان `verified` برداشته می‌شود.
- مالک نمی‌تواند تعلیق مدیر را بردارد؛ محتوای کسب‌وکار معلق قابل اصلاح است ولی وضعیت `suspended` و توضیح مدیر حفظ می‌شود.
- در حالت رد یا تعلیق، صفحه عمومی و QR پاسخ 404 می‌دهند؛ لینک و slug تغییر نمی‌کنند. بدون مشاهده نسخه قبلی عمومی، تغییرات تا تأیید مجدد منتشر نمی‌شوند.
- نشان‌های ویژه و مورد اعتماد مستقل از احراز هستند؛ فقط مدیر آن‌ها را تنظیم می‌کند. احراز، خودکار از صرفاً `approved` نتیجه‌گیری نمی‌شود.
- گالری رایگان جدید در جدول `business_images` است. داده قدیمی `showcases` مهاجرت داده‌ای یا حذف نشده و همچنان جزو ویترین اشتراکی قبلی است.
- محدودیت گالری با قفل رکورد کسب‌وکار در transaction کنترل می‌شود. برای رفتار همزمان واقعی باید روی PostgreSQL نیز تست انجام شود.

## نصب روی پروژه فعلی
1. از کد، دیتابیس و `storage/app/public` پشتیبان بگیرید؛ ابتدا در محیط staging انجام دهید. ZIP کامل را در پوشه جدا باز کنید یا فایل‌های ZIP تغییرات را با حفظ مسیر جایگزین کنید. فایل `.env` واقعی را با `.env.example` جایگزین نکنید.
2. در `api/.env`، مقادیر صحیح محیط را تنظیم کنید:
   ```dotenv
   APP_URL=https://api.example.com
   FRONTEND_URL=https://example.com
   CORS_ALLOWED_ORIGINS=https://example.com
   APP_ENV=production
   APP_DEBUG=false
   ```
   دامنه‌ها مثال هستند. CORS فهرست دقیق originهای مجاز با کامای انگلیسی و بدون مسیر/اسلش آخر است؛ `*` مجاز نیست. `FRONTEND_URL` مقصد Next.js است. برای لوکال: API روی `http://localhost:8000`، فرانت روی `http://localhost:3000`.
3. در `web/.env.local` یا تنظیمات build هاست:
   ```dotenv
   NEXT_PUBLIC_API_URL=https://api.example.com/api
   ```
   این متغیر باید هنگام build نیز حاضر باشد. مسیرهای فایل با `/api` و `/api/v1` پشتیبانی می‌شوند؛ `/api/v1` را فقط اگر سرور واقعاً این پیشوند را دارد استفاده کنید.
4. داخل `api/` اجرا کنید:
   ```sh
   composer install
   php artisan optimize:clear
   php artisan migrate
   php artisan storage:link
   php artisan db:seed --class=RoleSeeder
   php artisan db:seed --class=PermissionSeeder
   ```
   در production برای دستورهای نیازمند تأیید Laravel از `--force` طبق روال انتشار خودتان استفاده کنید. `migrate:fresh` روی دیتابیس واقعی اجرا نکنید. روی سایت موجود `APP_KEY` را عوض نکنید؛ روی نصب کاملاً جدید و بدون کلید، فقط یک بار `php artisan key:generate`.
5. مدیر جدید را تعاملی بسازید یا رمز مدیر قبلی را بچرخانید:
   ```sh
   php artisan admin:provision YOUR_ADMIN_MOBILE
   ```
   شماره باید `09...` باشد؛ رمز حداقل ۱۶ کاراکتر و دوبار پنهان دریافت می‌شود. ارتقای حساب غیرمدیر موجود انجام نمی‌شود. برای مدیر موجود، تأیید تغییر رمز و لغو توکن/کد بازیابی گرفته می‌شود.
6. داخل `web/` اجرا کنید:
   ```sh
   npm ci
   node --test tests/phase2-safety.test.cjs
   npx tsc --noEmit
   npm run lint
   npm run build
   ```
7. بعد از تأیید تست‌ها، cache کانفیگ/route/view را دوباره بسازید و سرویس‌ها را restart کنید. اگر از فایل start.sh پروژه استفاده می‌کنید، خطای migration دیگر مخفی نمی‌شود؛ فرایند در صورت شکست متوقف می‌شود.

## هشدار مهم درباره مدیر پیش‌فرض نسخه قبلی
در سورس ارسالی، seeder و یک migration رمز ثابت مدیر می‌ساختند یا بازنویسی می‌کردند. این رفتار در **نصب جدید** حذف شده است. نام migration قبلی حفظ شده ولی دیگر داده مدیر را تغییر نمی‌دهد.

**اگر آن migration قبلاً روی دیتابیس شما اجرا شده، تغییر فایل آن رمز موجود را عوض نمی‌کند.** پیش از انتشار با `admin:provision` رمز همان مدیر را عوض کنید؛ این دستور پس از تأیید، توکن‌ها و کد بازیابی قبلی او را لغو می‌کند. هیچ حساب موجودی با migration جدید حذف/غیرفعال نمی‌شود.

## کنترل‌های امنیتی و حدود آن‌ها
### XSS
- متن پروفایل در React به شکل متن render می‌شود، نه HTML خام. وارد کردن `<script>` در توضیحات، مجوز اجرای HTML نیست؛ داده متن ممکن است در دیتابیس بماند ولی به DOM خام تزریق نمی‌شود.
- لینک‌ها در API به HTTP/HTTPS معتبر محدودند؛ لینک دارای اطلاعات کاربری، کنترل‌کاراکتر یا بک‌اسلش رد می‌شود. فرانت لینک‌های قدیمی ناامن را نیز render نمی‌کند.
- SVG/HTML/PHP به عنوان تصویر جدید پذیرفته نمی‌شوند؛ فقط JPEG/PNG/WebP با MIME، حجم و ابعاد معتبر. نام و مسیر ذخیره را سرور می‌سازد؛ مالک مسیر تصویر دلخواه تعیین نمی‌کند.
- مسیر فایل‌های کسب‌وکار در Nginx نباید وارد PHP شود. برای Apache یا میزبان دیگر، تنظیم معادل عدم اجرای اسکریپت در storage را انجام دهید.
- توکن دیگر در cookie کمکی تکرار نمی‌شود؛ cookie فقط نشانگر ورود برای مسیریابی است، نه مجوز API.
- **توکن هنوز مطابق معماری پروژه در localStorage است؛ در صورت XSS در بخش دیگری از سایت قابل سرقت است.** مهاجرت به BFF یا cookie HttpOnly نیازمند طراحی جداگانه احراز هویت است. این نسخه ادعای حذف همه ریسک‌های XSS کل سامانه را ندارد. CSP کامل صفحه Next.js اعمال نشده چون نیازمند مدیریت nonce و تست سازگاری SSR است.

### SQL Injection
- ورودی‌ها از validation عبور می‌کنند؛ ذخیره/خواندن با Eloquent و Query Builder است.
- جستجو و PostGIS پارامتر bind می‌کنند؛ نام ستون‌ها فقط از فهرست ثابت کد می‌آیند. رشته جستجوی کاربر هرگز در SQL به عنوان دستور چسبانده نمی‌شود.
- این ادعا درباره مسیرهای فاز ۲ بازبینی‌شده است، نه ممیزی کامل تمام فازهای دیگر.

### CSRF
- API با Sanctum bearer token است و fallback به session وب برای API بسته شده است.
- درخواست تغییردهنده دارای Origin باید در allowlist دقیق باشد؛ HTML form ساده رد می‌شود. JSON یا multipart با `X-Requested-With: XMLHttpRequest` لازم است؛ این‌ها در مرورگر preflight ایجاد می‌کنند.
- cookie نشانگر رابط کاربری هیچ مجوزی برای عملیات API ایجاد نمی‌کند؛ CORS credentials خاموش است.
- مشتری CLI بدون Origin مجاز است ولی همچنان باید نوع محتوای درست و برای مسیرهای محافظت‌شده bearer معتبر داشته باشد.
- محافظ CSRF پیش‌فرض routeهای `web.php` حذف نشده. اگر بعداً Sanctum stateful SPA فعال شود، باید این معماری به جریان cookie + CSRF token تغییر کند؛ صرف اضافه‌کردن یک cookie کافی نیست.

### ثبت رخدادها
- جدول `audit_events`: ساخت، ویرایش، تغییر رسانه، حذف تصویر/کسب‌وکار، تصمیم مدیر و چرخش رمز مدیر. رخداد موفق کسب‌وکار در همان transaction تغییر داده درج می‌شود.
- `storage/logs/security-*.log`: درخواست‌های ورود/خروج و بازیابی موفق/ناموفق، رد درخواست API، خطاهای اعتبارسنجی/مجوز و محدودیت نرخ از طریق middleware پایان درخواست. نام route، کد پاسخ و عامل ثبت می‌شوند؛ token، رمز، OTP، متن فرم و اطلاعات تماس ثبت نمی‌شوند. IP به شکل HMAC ثبت می‌شود.
- تاریخچه کسب‌وکار از پنل مدیر قابل خواندن است؛ تاریخچه کسب‌وکار حذف‌شده در DB باقی می‌ماند و برای بررسی عملیاتی از دسترسی مجاز دیتابیس استفاده کنید.
- رخدادهای گذشته بازسازی نمی‌شوند. لاگ‌ها برای اثبات غیرقابل‌دستکاری بودن کافی نیستند؛ دسترسی UPDATE/DELETE جدول audit را برای کاربران غیرضروری ببندید و لاگ‌ها را به مقصد مرکزی/آرشیو محافظت‌شده ارسال کنید.
- فایل‌های رسانه هنگام حذف کامل کسب‌وکار نگه داشته می‌شوند تا ارجاع فازهای دیگر ناخواسته شکسته نشود. برای پاکسازی orphanها سیاست نگهداری و ابزار کنترل‌شده جداگانه لازم است؛ جایگزینی لوگو/کاور و حذف تکی گالری فایل قدیمی را پاک می‌کند.

## تست‌های موجود و نتیجه واقعی این تحویل
**اجراشده در محیط تهیه خروجی:**
- ۲۲ تست مستقل توابع URL، مسیر تصویر و واتساپ: موفق.
- تبدیل نحوی ۶۱ فایل TypeScript/TSX پروژه: بدون خطای نحوی گزارش‌شده. این آزمون جای type-check کامل را نمی‌گیرد.
- bundle سه صفحه اصلی فاز ۲ با وابستگی‌های خارجی خارج از bundle: موفق؛ این آزمون `next build` نیست.

**آماده اجرا، اما اجرا نشده:**
```sh
cd api
php artisan test --filter=PhaseTwoAcceptanceTest
php artisan test --filter=PhaseTwoSecurityTest
php artisan test
```
برای تست تصاویر، GD و درایور SQLite محیط تست لازم‌اند؛ تست‌های backend این پروژه SQLite حافظه‌ای دارند. سپس آزمون PostgreSQL/PostGIS و storage واقعی را جداگانه انجام دهید. هیچ تست PHP یا تأیید عملی deployment در این تحویل ادعا نشده است.

## چک‌لیست مرورگر و پذیرش نهایی
- کاربر عادی اولین کسب‌وکار را ثبت کند؛ نقش مالک از سمت سرور داده شود.
- تمام فیلدها را پر کنید، ذخیره کنید، صفحه را reload کنید و تطابق را بررسی کنید.
- تلفن/شهر/محله/خدمات/لینک‌ها را پاک کنید و ذخیره/بازخوانی را چک کنید. مختصات را جفتی پاک کنید و در PostgreSQL، geom نیز NULL شود.
- تصاویر معتبر آپلود شوند، SVG/فایل جعلی/حجم زیاد رد شوند؛ ششمین عکس حتی با درخواست مستقیم API رد شود.
- مالک دوم نتواند شناسه پروفایل یا تصویر دیگری را بخواند/ویرایش/حذف کند.
- مدیر تأیید کند و لینک عمومی در پنجره ناشناس با اطلاعات صحیح باز شود؛ QR را با دوربین گوشی اسکن کنید و دامنه/slug را بررسی کنید.
- مدیر رد یا تعلیق کند؛ لینک عمومی و QR دیگر قابل دریافت نباشند؛ دلیل در پنل مالک نمایش داده شود.
- تغییر مالک، تعلیق را برندارد؛ تأییدشده با تغییر واقعی به pending برود؛ ذخیره بدون تغییر آن را بی‌دلیل pending نکند.
- ورود از origin غیرمجاز، cookie بدون bearer و فرم ساده برای mutation رد شوند؛ JSON و multipart از فرانت مجاز کار کنند.
- بررسی کنید متن HTML در پروفایل فقط متن است؛ لینک `javascript:` پذیرفته/اجرا نمی‌شود؛ رشته SQL در نام هیچ دستوری اجرا نمی‌کند.
- رخدادهای DB و لاگ فایل بعد از یک درخواست واقعی HTTP موجود باشند؛ ذخیره روی volume پایدار باشد و فایل log از وب قابل دانلود نباشد.
- روی موبایل، شبکه کند، خطای آپلود، منقضی‌شدن توکن و قطع API تست کنید. یک درخواست ذخیره ممکن است موفق شده باشد ولی پاسخ آن گم شود؛ قبل از تکرار ثبت جدید، فهرست را بازخوانی کنید.

## بازگشت به نسخه قبلی
کد و داده را جداگانه بازیابی کنید. rollback migration جدید جدول‌های گالری و audit را حذف می‌کند؛ برای بازگشت production آن را بدون backup اجرا نکنید. خروجی کامل شامل همه فایل‌های قبلی و جایگزین‌های جدید است؛ ZIP تغییرات فقط مسیرهای جدید/ویرایش‌شده را دارد. هیچ script نصب خودکاری در این ZIP برای اعمال تغییرات روی سیستم شما اجرا نشده است.
